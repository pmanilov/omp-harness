# Работа и проверки в OMP

## Планирование

Оставляем формат и последовательность планирования OMP по умолчанию. `global/AGENTS.md` добавляет условие для блока **«Тестирование»** в плане реализации: когда меняется наблюдаемое поведение или публичный контракт, назвать сценарий, способ проверки и ожидаемый результат. Сценарий важнее списка команд. Не вводим универсальный шаблон плана и не требуем тестов для анализа или обычной правки документации.

Пример для исправления ошибки: «Тестирование: воспроизвести ошибку на минимальном входе; после исправления запустить существующий тест для этого входа и прямой вызов изменённой функции; ожидание — корректный результат при граничном значении и сохранение соседнего случая». Конкретное имя теста/команду вписывают **после** изучения целевого проекта, не копируют отсюда.

Пример для текстовой правки без изменения поведения: блок «Тестирование» не нужен; при необходимости проверить ссылки, формат или обязательную проверку репозитория, но не создавать фиктивный тест поведения.

После правок в этом репозитории проверяйте читаемость `AGENTS.md` и примера плана в OMP, затем `git diff --check` и `git status --short`.

## Git staging

После реализации изменений, если правила проекта не запрещают staging, проверить созданные для задачи файлы и добавить в индекс только неигнорируемые через `git add -- <конкретные файлы>`. Не добавлять существовавшие до задачи неотслеживаемые файлы, изменения отслеживаемых файлов и посторонние пути без запроса. Не применять широкое или принудительное добавление и не создавать коммит без запроса.

## Синхронизация настроек агента

Общие настройки хранятся в `global/config.yml`; способ подключения через `omp --config` описан в [README](../README.md#общие-настройки-агента). Файл — источник общих настроек, а не снимок всего каталога агента. Локальные endpoints, учётные данные, согласия и runtime-состояние не переносим. Действующую пользовательскую конфигурацию автоматически не заменяем.

При изменении настроек проверяйте загрузку дополнительного слоя в OMP и затронутый сценарий; синтаксического разбора YAML недостаточно для проверки применения настроек. Изменения ролей моделей требуют доступности выбранных моделей на целевой машине.

## Проектная документация

При создании нового проекта по запросу пользователя агент создаёт полезную Markdown-документацию вместе с реализацией, используя skill `project-docs`, когда он доступен. Для существующего репозитория генерация комплекта требует явного запроса: начало сессии и отсутствие документов не являются поводом для записи. Запрос на review или исследование также не разрешает правки; узкий запрос ограничивается названным аспектом.

Перед изменением проекта агент читает релевантную документацию и актуализирует затронутые аспекты в той же задаче. Существующие язык, пути и владельцы тем сохраняются. Например, изменение команды запуска требует правки существующей инструкции локальной разработки и относящегося к ней примера README, а не создания второго руководства.

Значимое решение записывается в ADR только с известным контекстом или при прямо согласованном новом решении. Например, согласованный выбор хранилища с известными ограничениями и последствиями можно зафиксировать; обнаруженный в коде драйвер сам по себе не доказывает историю принятия решения.

Формат, условные аспекты и правила ADR описаны в [единственном подробном reference](../skills/project-docs/references/format.md); установка и пользовательские вызовы — в [README](../README.md#проектная-документация). AGENTS остаётся короткой инструкцией/индексом, а не копией или импортом всех документов. Без подключённого skill используйте соглашения проекта и сообщайте о недоступности workflow харнесса.

Проверяйте локальные ссылки и подтверждённость утверждений; безопасные доступные примеры можно запустить напрямую. Отличайте прочитанную команду от реально выполненной. Для обычной текстовой правки не создавайте искусственные поведенческие тесты; изменение поведения инструкций проверяйте прямым сценарием OMP.
