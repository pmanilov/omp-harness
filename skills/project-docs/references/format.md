# Формат проектной документации

Это стартовая карта аспектов, а не обязательный комплект файлов. Документ создаётся только при наличии полезного подтверждённого содержания. Существующие пути, язык и владельцы тем имеют приоритет над именами по умолчанию: `CONTRIBUTING.md`, `doc/design.md`, страницы сайта документации или содержательные разделы README могут полностью закрывать аспект. Не переименовывайте их и не создавайте параллельные документы.

## Общий Markdown-формат

Один заголовок первого уровня на документ; основные разделы — второго уровня. Используйте относительные ссылки на документы и реализацию. Блоки команд снабжайте языком, указывайте рабочий каталог, необходимые переменные окружения без секретных значений и условия запуска. Для примера запуска приводите ожидаемый наблюдаемый результат. Прочитанная команда не равнозначна выполненной проверке.

Не требуются YAML-метаданные, диаграммы, заданный размер файла или инструмент публикации. Не создавайте разделы без содержания. Диаграммы допустимы только для подтверждённых компонентов и связей. Отделяйте текущую реализацию от согласованных требований и планов; не выдавайте будущую реализацию за существующую.

## Аспекты и имена по умолчанию

| Аспект | Новый проект с реализацией | Содержание |
| --- | --- | --- |
| Назначение и входная точка | `README.md` | Для кого и какую задачу решает проект; подтверждённые границы; минимальный запуск или использование с ожидаемым результатом; ссылки на остальные существующие документы. |
| Устройство | `docs/ARCHITECTURE.md` | Граница системы и внешние участники; основные компоненты со ссылками на пути реализации; один основной поток данных или выполнения; важные подтверждённые ограничения; ссылки на записанные решения, если они есть. Не пересказ каждого файла. |
| Разработка | `docs/DEVELOPMENT.md` | Подтверждённые требования к окружению; настройка и локальный запуск; существующие команды проверок; практический сценарий изменения и проверки; существенные ограничения или отсутствие автоматизированных проверок. Не придумывайте CI и зависимости. |
| Эксплуатация, условно | `docs/OPERATIONS.md` | Только при подтверждённом развёртывании или обслуживании работающей системы: конфигурация без секретов, запуск и остановка, проверка здоровья, диагностика. Восстановление и откат — только при известных процедурах. |
| Значимые решения, условно | `docs/decisions/NNNN-title.md` | Только при подтверждённом контексте решения или прямо согласованном новом решении. Один файл — одно решение. |

В проекте без реализации и технических решений создавайте только README с известным назначением и явно обозначенными планируемыми требованиями. Остальные документы появляются вместе с подтверждённым содержанием; не создавайте пустые каталоги ради будущего комплекта.

## Записи архитектурных решений

Для нового ADR используйте заголовок `# ADR NNNN: <название>` и разделы `## Status`, `## Context`, `## Decision`, `## Consequences`. Статусы: `proposed`, `accepted`, `deprecated`, `superseded`. При замене сохраняйте прежнюю запись и добавляйте ссылку на новый ADR. Новые номера последовательные с `0001`, без переиспользования.

В существующем ADR-каталоге сохраняйте его формат и нумерацию. Код сам по себе не подтверждает историческую мотивацию или согласование решения: не выпускайте реконструированные `accepted` ADR. Если контекст неизвестен, сообщите этот пробел вместо придуманной истории.

## Справка и практические инструкции

Для API, CLI и параметров конфигурации ссылайтесь на существующие контракты, схемы, `--help` или генерируемую справку. Не создавайте дополнительный справочник ради комплекта. Содержательный how-to помещайте в документ соответствующего аспекта; заранее не создавайте отдельные каталоги tutorials/reference.

## Обоснование и источники

Набор файлов выше — синтез для OMP Harness, а не обязательный стандарт перечисленных авторов:

- [Diátaxis: применение](https://diataxis.fr/application/) разделяет инструкции, справку и объяснение; [практический подход](https://diataxis.fr/how-to-use-diataxis/) предостерегает от пустых структур.
- [arc42 Canvas](https://arc42.org/canvas/) позволяет кратко описать границы, компоненты, взаимодействия и ограничения без полного шаблона архитектуры.
- [Michael Nygard: Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions.html) предлагает небольшую запись одного решения с контекстом, статусом и последствиями, сохраняя историю замен.
- [Write the Docs: Docs as Code](https://www.writethedocs.org/guide/docs-as-code/) связывает документацию с Git и review; [начальный гайд](https://www.writethedocs.org/guide/writing/beginners-guide-to-docs/) рекомендует начать с назначения, установки и примера использования.
- [Red Hat: AGENTS.md and Agent Skills](https://developers.redhat.com/articles/2026/07/27/standardize-project-context-agentsmd-and-agent-skills) поддерживает короткий индекс в постоянно загружаемом контексте вместо полного корпуса документации.
