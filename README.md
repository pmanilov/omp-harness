# OMP Harness

Короткие инструкции для OMP: блок «Тестирование» в планах изменений поведения, добавление новых файлов в Git с учётом правил проекта и полезная проектная документация вместе с созданием проекта. Skill `project-docs` даёт переиспользуемый workflow для создания, проверки и актуализации документации.

## Что где находится

- `AGENTS.md` — инструкции для работы **в этом репозитории**; OMP обнаруживает корневой файл автоматически.
- `global/AGENTS.md` — общие правила для работы **во всех проектах** после подключения к пользовательскому контексту OMP.
- `global/config.yml` — общие настройки агента: роли моделей, интерфейс, память и отключённые расширения; установщик связывает их с пользовательским конфигом.
- `docs/WORKFLOW.md` — примеры блока «Тестирование», пояснение Git staging и работы с проектной документацией.
- `extensions/codex-usage.ts` — источник расширения OMP для статуса лимитов Codex; установка описана ниже.
- [skills/project-docs/SKILL.md](skills/project-docs/SKILL.md) — workflow проектной документации для OMP.
- `install.sh` — установщик символических ссылок на конфигурацию, общие инструкции и skills.
- [skills/project-docs/references/format.md](skills/project-docs/references/format.md) — канонический Markdown-формат и карта аспектов.

## Подключение в OMP

Из любого рабочего каталога запустите установщик по пути к клонированному репозиторию:

```sh
/полный/путь/к/omp-harness/install.sh
```

Он создаёт **символические ссылки**, а не копии:

- `~/.omp/agent/config.yml` → `global/config.yml`;
- `~/.omp/agent/AGENTS.md` → `global/AGENTS.md`;
- `~/.omp/agent/skills/<имя>` → соответствующий каталог в `skills/` с `SKILL.md`.

Повторный запуск сохраняет уже правильные ссылки. Если хотя бы один целевой путь занят другим файлом, каталогом или ссылкой, установка прекращается до изменений. Для замены с сохранением старых путей используйте:

```sh
/полный/путь/к/omp-harness/install.sh --backup
```

Резервная копия конфликтующих путей сохраняется в новом каталоге `omp-harness-backup.*` внутри каталога агента; установщик выводит его путь. Старые настройки и инструкции **не объединяются** с файлами харнесса. Нужные пользовательские правила и параметры из копии перенесите самостоятельно, учитывая, что файлы харнесса отслеживаются Git. Установка не затрагивает auth, сессии, базы, кэши и расширения.

По умолчанию используется `PI_CODING_AGENT_DIR`, если он задан, иначе `~/.omp/agent`. Другой каталог, в том числе каталог профиля, можно указать явно:

```sh
/полный/путь/к/omp-harness/install.sh --agent-dir /путь/к/каталогу/агента
```

Нужны Bash и стандартные Linux-утилиты, включая `realpath` и `mktemp`. Репозиторий должен оставаться по прежнему пути: ссылки абсолютные. После перемещения репозитория повторите установку с `--backup`, чтобы заменить старые ссылки. Откройте новую TUI-сессию `omp` и проверьте контекст и skills через `/extensions`.

## Общие настройки агента

После установки запускайте обычный `omp`: пользовательский `config.yml` уже ссылается на `global/config.yml`, аргумент `--config` и shell-обёртка не нужны.

Изменения пользовательских настроек через UI агента или `omp config set` записываются **в `global/config.yml` этого репозитория**, сохраняя ссылку. Например:

```sh
omp config set theme.dark titanium
```

Это относится к установленному каталогу агента; для другого каталога или профиля запускайте OMP с соответствующим окружением или профилем. Настройки уровня проекта остаются в проекте. Инструкции и skills также редактируются по ссылкам в исходных файлах харнесса. Изменения можно переносить через Git; после `git pull` новые настройки загружаются при следующем запуске.

**Не сохраняйте секреты и машинные параметры в связанном пользовательском конфиге.** Локальный proxy `providers.openai-codex.baseUrl`, учётные данные, `setupVersion` и `dev.autoqaConsent` намеренно отсутствуют в исходном файле. После замены старого конфига они не применяются автоматически из резервной копии. Если нужны машинные настройки, храните их в отдельном локальном YAML вне репозитория и запускайте `omp --config /путь/к/локальному.yml`; не вносите их через настройки связанного пользовательского конфига. Доступ к моделям и backend памяти `mnemopi` настраивается на каждой машине отдельно.

Не связывайте весь каталог `~/.omp/agent` с репозиторием: auth, сессии, базы и кэши должны оставаться локальными. Перед коммитом изменений конфига проверяйте, что OMP не записал в него машинное состояние.

## Проектная документация

При запросе создать новый проект агент пишет полезную документацию вместе с реализацией; отдельная команда не нужна. В существующем проекте комплект генерируется только по явному запросу, а затронутые изменениями документы актуализируются в той же задаче. Создание каталога сторонней программой и открытие сессии OMP сами по себе ничего не генерируют.

Аспекты: назначение и использование, устройство, локальная разработка; эксплуатация и значимые решения — только при подтверждённом содержании. Существующие пути и язык имеют приоритет: не создаём дубли `CONTRIBUTING.md`, `doc/design.md` или разделов README. Для проекта без реализации достаточно README с назначением и явно планируемыми требованиями. Подробности и имена по умолчанию — в [каноническом формате](skills/project-docs/references/format.md).

Skills подключаются установщиком из раздела [«Подключение в OMP»](#подключение-в-omp): каждый каталог с `SKILL.md` получает отдельную ссылку в каталоге `skills` агента. Подробный reference в пользовательский контекст не импортируйте.

После подключения откройте новую TUI-сессию `omp` и в `/extensions` проверьте обнаруженный `project-docs` с источником из харнесса. После изменения skill начните новую сессию или выполните `/reload-plugins`.

```text
# Новый проект: обычный запрос агенту, отдельная команда не нужна.
Создай новый проект <описание>.

# Существующий: интерактивная команда OMP.
/skill:project-docs
/skill:project-docs Обнови только инструкции локальной разработки.
```

Slash-вызов требует включённых skill commands. Когда skill обнаружен, но slash-команды отключены, используйте естественный запрос: «Используй skill project-docs для документации этого проекта». Если навыки полностью отключены, этот workflow недоступен до их подключения. Без доступного skill агент следует существующим соглашениям проекта и сообщает, что workflow харнесса не подключён, а не выдумывает доступ к нему.

## Статус лимитов Codex

`extensions/codex-usage.ts` — расширение для основного TUI OMP. Оно получает отчёты через `ctx.modelRegistry.authStorage.usage.reports()`, без вызова `omp usage` как отдельного процесса, и выбирает отчёт OAuth-аккаунта текущей сессии. В статусе показывает оставшийся процент по окнам `5h` и `7d` и время до `window.resetsAt` в скобках: например, `5h 68% (14m) · 7d 54% (4d 5h)`. Для `5h` время округляется вверх до минуты, для `7d` — до часа и выводится без минут. Если время сброса неизвестно, скобки не выводятся.

Первый опрос выполняется при старте сессии, затем каждые 30 секунд; при переключении сессии статус обновляется сразу. Без OAuth-учётных данных статус скрывается, при ошибке получения отчёта показывается `?`. Строка передаётся через `ctx.ui.setStatus("codex-usage", …)` и отображается, когда в конфигурации `statusLine` включён сегмент `status`.

Для установки из корня клонированного репозитория (если по целевому пути ещё нет файла) создайте ссылку на источник:

```sh
mkdir -p ~/.omp/agent/extensions
ln -s "$(pwd)/extensions/codex-usage.ts" ~/.omp/agent/extensions/codex-usage.ts
```

В этой установке ссылка `~/.omp/agent/extensions/codex-usage.ts` относительная и ведёт на `~/omp-harness/extensions/codex-usage.ts`. OMP обнаруживает расширение в каталоге агента при запуске новой TUI-сессии; хранить код отдельно в `~/.omp/agent/extensions` не нужно.
